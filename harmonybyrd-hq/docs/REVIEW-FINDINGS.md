# Adversarial review: findings and what was done
Generated from the review's own output, the fix reports and the re-check results. Do not edit by hand.

## How the review was done
After the application was first delivered, seven reviewers who had not written it were each given one lens and told to assume it contained real defects. Each worked in a database of its own, attacked the application as every role, and reported only what it could point at precisely. A second reviewer then took each finding separately and tried to refute it: a finding counts only if that second reviewer reproduced it with something it ran (or, for documentation and test-quality findings, by quoting the lines that contradict each other).
**71 findings were confirmed and none was refuted**: 0 critical, 2 high, 25 medium, 44 low. Several describe the same root cause seen through different lenses; they are listed separately, as reported.
The fixes were made in rounds. After each round, verifiers who had not made the fixes ran the attacks again against the fixed code and tried close variations (a “re-check”). What a re-check showed to be open was fixed in the next round. The rounds and what each re-check found are set out below.
The reviewers, fixers and verifiers were AI agents working under the builder's direction. This is a sceptical pass by the same build process, not an assessment by an independent person; that remains a recommendation.

## What the review showed, in short
- **The serious weakness was the proposal path.** A proposal accepted in good faith could carry invented quotations, text labelled as checked by HQ, or changed checksums, and the screens then showed that text exactly like import-verified material. Quotations were verified only when a pack was imported. No non-founder could apply such a proposal alone, but the review screen gave the founder no warning.
- A founder acceptance stayed attached to a record after a later proposal changed what had been accepted.
- A quotation made only of spaces passed the verbatim check.
- Sign-in: the throttle could be bypassed and used to lock the founder out; an open redirect after sign-in; signing out did not end the session.
- Several tests would have stayed green if the protection they claim to test had been deleted (shown by mutating the database and re-running the suite).
- **What held under attack:** no non-founder could write a record, read another client's proposals or any secret, or record an acceptance; forged, unsigned, expired and wrong-kind tokens and sessions were refused; no SQL was built from input; a re-import never overwrote a record changed through governance.
