# Engineering decisions

Decisions made while building HQ, with the reason for each. They are the builder's decisions and
are open to review; none of them is a founder ruling.

| # | Decision | Reason | Alternative set aside |
| --- | --- | --- | --- |
| 1 | Build HQ as an isolated, non-authoritative prototype | The commission makes HB-AI-P00 the prerequisite and says what to do if its acceptance cannot be verified. It could not be verified | Treating HQ as authoritative; stopping until P00 is found |
| 2 | Keep the commission's preferred stack | Nothing in the evidence gave a reason to change it | — |
| 3 | Run on plain PostgreSQL, following Supabase conventions | No Supabase credentials. The same migrations, roles, claims and row-level security are intended to run on Supabase unchanged; that is untested | Mocking the database; an embedded database that lacks row-level security |
| 4 | Store records as versioned JSON documents in one append-only table, validated by typed schemas | Twelve record types with nested, cited claims; history, pinning and hashing become uniform; schema changes do not rewrite history | One relational table per type with history tables |
| 5 | A dataset revision for every write, with a content hash | Gives pinned reads, stale-write detection and a tamper-evident history from one mechanism | Per-record versions only |
| 6 | Enforce governance in the database (triggers, definer functions, row-level security) | A rule that lives only in application code is bypassed by the next client. The tests go round the application to prove the database refuses | Checks in the API layer only |
| 7 | The application's database role owns nothing | Limits the damage of an application bug | Connecting as the owner |
| 8 | Every fact is a claim with an epistemic label and verbatim citations; the importer verifies each quotation | It is the only mechanical guard against manufactured records | Free-text notes with links |
| 9 | Twelve independent lifecycle dimensions; no completion percentage | The commission requires it, and a single number would hide exactly the distinctions that matter | A status enum |
| 10 | “Accepted” in HQ exists only as the effect of a founder decision; acceptance reported by a document is shown separately | So that neither a document nor an agent can make HQ call something accepted | A status field anyone with write access could set |
| 11 | No approval tool, and no token for the founder | Founder authority cannot then be exercised by a script or an assistant, even by mistake | A privileged “admin” token |
| 12 | One tool registry behind both REST and MCP | The two interfaces cannot drift apart | Separate handlers |
| 13 | Stateless MCP over Streamable HTTP with JSON responses | Simplest correct server for request/response tools; no session state to secure | Stateful sessions with server-sent events |
| 14 | Static bearer tokens now; OAuth 2.1 recommended as its own commission | Tokens are enough for a local prototype and for clients that accept a header. OAuth is a security-sensitive feature that deserves its own review and is only needed once a deployment is authorised | Implementing OAuth in this commission |
| 15 | Own passphrase sign-in rather than Supabase Auth | No Supabase project. The session token uses the same core claims (`sub`, `role`), so moving to Supabase Auth is a contained change; since the review it also carries HQ's issuer and a session epoch, which Supabase tokens do not | Blocking on Supabase |
| 16 | Read-only GitHub and Drive adapters that return failure values | The commission authorises preparation, not broader writes; an unavailable service must never break a page or be papered over | Write-capable integrations |
| 17 | Evidence packs as files, built outside the application | Reading documents and turning them into cited records needs judgement and an audit trail; the application's job is to verify and hold the result | An upload-and-parse screen |
| 18 | Keep the real evidence pack and source snapshots out of the repository | The working repository is public. The founder's documents are private and were not authorised for publication | Committing the pack |
| 19 | Three accessible artefacts of a different product inventoried but not ingested | They do not describe HarmonyByrd | Mixing them into the HarmonyByrd atlas |
| 20 | Merge records only where identity is certain; otherwise cross-reference | Two documents' mentions of one build or decision should be one record, but a wrong merge would manufacture a fact | Merging by similar name |
| 21 | When two documents disagree about a module's state, show the more cautious reading and list the other | Never upgrade a status on the strength of the more optimistic source | Taking the latest, or the owner's |
| 22 | Server-rendered pages with native disclosure elements and links; almost no client-side code | Fast, works without JavaScript for reading, nothing floating over content | A client-side single-page application |
| 23 | Paging and folding for long registers | With real volumes (hundreds of items) an unpaged list is unusable; folding hides nothing permanently and always states the count | Infinite scroll |

## Decisions made when fixing the adversarial review's findings

Numbers 24 to 41 correspond to design decisions D1 to D18 of the fix stages; docs/REVIEW-FINDINGS.md
lists the findings each one answers.

| # | Decision | Reason | Alternative set aside |
| --- | --- | --- | --- |
| 24 | A proposal cannot assert what HQ did not check: its quotations are verified against source texts stored at import, HQ's own labels are refused, source labels need citations (replaced by 70: a source label is now set only by an import), and HQ-written fields are protected — at submission and again at acceptance (D1) | The inbox is where claims enter; a founder accepting in good faith must not turn a submitter's words into "verified" text | Trusting the founder's review to catch it |
| 25 | A record carrying a founder acceptance or rejection cannot be changed by proposal; the decision stores the version it accepted (D2) | An acceptance binds to what was accepted, not to whatever the record later becomes | Carrying the acceptance over; marking it stale |
| 26 | The write context is an owner-only table keyed by transaction, not a session setting, and versions go only into the open, latest revision (D3) | Any role that could set the setting could forge a founder act | Checking the setting more carefully |
| 27 | Revision seals form a chain, and the latest seal is shown so the founder can keep a copy outside HQ (D4) | The database owner can rewrite history and seals together; only an outside copy shows it | Claiming the history is "verified" |
| 28 | API roles cannot write the audit log directly; the application writes refusals through narrow wrappers, in their own transaction (D5) | A free-form writer let any token forge audit rows, and refusals inside the database roll their own record back | Auditing inside each refusing function (it cannot persist); a loopback connection (adds an extension and a credential) |
| 29 | Proposal events follow a fixed order enforced by a trigger, and withdraw takes the same lock as review (D6) | Withdraw and accept could both succeed | Relying on the application to serialise them |
| 30 | Sessions carry an epoch; signing out or a new passphrase increments it (D7) | Sign-out only deleted the cookie, so a copied cookie stayed valid for twelve hours | A list of revoked tokens |
| 31 | Sign-in is delayed, never locked, with a delay kept per lane (a name, or a name and a device since 46), and `X-Forwarded-For` is ignored unless a trusted proxy is declared (D8) | Keying on a client-supplied header let a guesser bypass the limit and let anyone lock the founder out | A hard lock-out per name and address (the queue this kept was replaced by 46) |
| 32 | Every JSON body is capped; each MCP batch message is answered on its own; query values are converted only as each tool declares (D9) | An unbounded body, one bad batch element or guessed types should not break other requests | Per-route limits |
| 33 | Setup makes the secret-bearing files owner-only on every run (D10) | A file copied by hand was readable by everyone on the machine | Only setting permissions when setup creates the file |
| 34 | Quotations need at least twelve characters and exact wording at least eight non-space characters after normalising; ids of the form `XX-HQ-n` are reserved; the import records which pack it was (D11) | A quotation of spaces matched any source; a pack could take ids HQ issues | Changing the normalisation itself |
| 35 | Derived figures count only what a source supports or HQ's build checked; a rejection in HQ has its own standing; dates never break a page; inbox-origin records count as unverified (D12) | Several figures could be raised by an uncited claim or hide a rejection | Leaving the figures and adding warnings |
| 36 | A founder decision may name only records that exist (D13) | A decision resolving a misspelt id would look complete and resolve nothing | Accepting free text |
| 37 | A pinned screen keeps the pin on every link and shows a bar; screens that act on the present always show the latest and say so (D14) | Pinned pages mixed in the latest data and links silently left the pin | Pinning every screen, including the decision forms |
| 38 | Fields only HQ's build writes are declared with exact types and cannot be proposed (D15) | Loose values crashed screens and could be set by proposal | Leaving them undeclared |
| 39 | Screens render declared fields through type guards; a refused review in a second tab says why; bad addresses give 404 or 400, not 500 (D16) | A robust screen must not crash or stay silent on odd input | Error pages only |
| 40 | Every tool returns the envelope and refuses arguments it does not take; live look-ups need a signed-in person, and Drive look-ups a listed file id (D17) | A silently ignored `rev` gave head data to a client that asked for a pinned revision; any token could make HQ query the founder's Drive | Documenting the exceptions only |
| 41 | Setup fills placeholders in an existing `.env.local`, and the application refuses to start with a placeholder or short secret (D18) | The published placeholder could become the database password, and a short secret broke every sign-in | Telling people to replace them by hand |

## Decisions made after the re-verification

Every original attack was re-run against the fixes. Numbers 42 to 53 correspond to the follow-up
decisions F1 to F12; docs/REVIEW-FINDINGS.md lists the findings each one answers.

| # | Decision | Reason | Alternative set aside |
| --- | --- | --- | --- |
| 42 | A proposal can never introduce a claim of acceptance: a build standing `accepted_reported`, a module `founder_accepted` of `yes` or `partial`, or a `founder_accepted` field is refused (HQ403), at submission and again at acceptance; a build marked as accepted without a quoted report is shown as “Acceptance claimed — no source quoted” (F1) | A verbatim quotation proves the words are in a source, not that they report an acceptance | Requiring a citation for the claim |
| 43 | Only founder-acceptance evidence for that build, or an issued HQ decision whose `set_acceptance` accepts it, counts as an acceptance instrument (F2) | A decision about the module, a decision a source reports, or a link the build carries could silence the review item, and a proposal can set links | Counting any decision linked to the build or its module (the cautious rule lists more builds for review) |
| 44 | `service_role` may execute only the read helpers; EXECUTE is revoked from the catalogue, and a test reads the catalogue so that a later function cannot be left open (F3) | It could call the founder functions with forged claims | Revoking function by function; changing the database's default privileges, which would reach beyond HQ's schema |
| 45 | `hq.log_access` accepts only the action families the application logs as allowed (since 80, an exact list); founder acts are logged only by the functions that perform them; new audit details are capped at 16,384 bytes (F4) | Any signed-in caller could write an allowed row for a founder act it never performed | Checking the caller's role in the wrapper |
| 46 | Sign-in attempts no longer queue: each waits on its own, work in progress is bounded, and a browser that has signed in before gets its own lane through a device cookie that authenticates nothing; device lanes are limited per person, never across people (F5) | The queue let open wrong attempts hold the right passphrase back for minutes | A lock-out; keying on the client's address; one limit shared by all device lanes, which any account holder could fill |
| 47 | The request id is always the server's; a client's well-formed id is kept apart as `x-client-request-id` and `detail.client_request_id` (F6) | A client could give its request the id of another request in the audit log | Keeping the client's id when well formed |
| 48 | A record carrying a founder rejection is called a rejection in the refusal message (F7) | The message said “acceptance” for a rejected record | Leaving the wording |
| 49 | A pack's `hq_verified` evidence and `verified` claims are taken as recorded; this is documented, not re-checked (F8) | The import can re-verify quotations, not the checks a builder ran | Re-running checks at import (out of scope) |
| 50 | The founder's review screen lists the sources a proposed record cites, with whether HQ holds their text, and calls out any change to a record's standing fields (F9) | A create proposal showed “No source is recorded for the target” | Showing only the target's sources |
| 51 | Chip labels wrap inside their box, and sideways scroll is measured against the layout viewport (F10) | A long label ran past a phone screen, and the phone test could not see it | Shortening the label only |
| 52 | The covering detector also checks what is drawn at points over text, so shifted blocks and pseudo-element overlays are found (F11) | It checked only positioned elements and what lies over the main content | Screenshot comparison |
| 53 | A unit test pins the session lifetime at exactly twelve hours (F12) | The old test compared the lifetime with the constant that sets it | Trusting the constant |

## Decisions made after the re-check of the second round

The second round was re-checked (docs/PROGRESS-REGISTER.md). Numbers 54 to 66 correspond to the
third-round decisions G1a to G1f, G2, G3, G4 and G6 to G9; G5 and G10 are the corrections to these
documents. Numbers 67 to 69 are G11a to G11c, which finished the round: the conformed view for every
reader, one proposal-impact function, and the passphrase limit when one is set.

| # | Decision | Reason | Alternative set aside |
| --- | --- | --- | --- |
| 54 | A build a source reports as accepted is frozen for proposals: every change is refused (HQ403) unless the proposal withdraws the report by giving it another valid standing (G1a) | Comparing only the standing let a proposal relabel a claim as a report, widen what was accepted, or move the acceptance to another module | Binding only the statement, which left module, label and artifact open |
| 55 | A module's reported founder acceptance must stay identical as a whole entry, and any state but exactly `no`, `unknown` or `not_applicable` counts as positive (G1b) | Comparing four named keys let a proposal add a `scope`; matching `yes` and `partial` exactly let `Yes` or `yes ` through | — |
| 56 | The database checks the values that drive labels itself, from a table of allowed values (`hq.field_enums`) kept equal to the schemas' lists by a test. Created records are checked in full; for an update, the fields it sets, and always the fields that drive acceptance (G1c) | A caller that went round the application could store `accepted`, `Yes` or a list, which screens showed as acceptance or failed on | Checking every field of the stored record on every update, which would block ordinary edits of records imported before the rule |
| 57 | Accepting a proposal through the application validates the whole record as it would then stand, inside the acceptance's transaction, and before the stale check when the target has moved on; a failure is 422 and the proposal stays submitted (G1d) | A proposal planted straight in the inbox could leave a record no import would take | — |
| 58 | A founder decision counts as an acceptance instrument only while the build's current HQ acceptance is *accepted* and names it (G1e) | An acceptance the founder later cleared still silenced the review item | Counting any issued decision that accepts the build (the earlier rule) |
| 59 | Screens show a stored record that fails validation conformed to its schema: a wrong value reads “Not a valid value”, a reference HQ does not hold is not a link, and nothing odd can read as accepted (G1f); since 67, every reader does | One odd value made a page fail, or the whole navigation | — |
| 60 | Audit action names are bounded (80 characters; each allowed family with a length limit and no dot inside a name), and no name that reads like a founder act can be recorded as allowed (G2; the list of refused words this used was replaced by the exact list of 80) | The action column had no limit, so the detail size limit could be got round, and names such as `api.decision.record` could be written | Listing every exact name the application logs |
| 61 | The request id a direct database caller passes is documented as a limit, not changed (G3) | The database cannot know the application server's id | Having the database make the id and return it |
| 62 | HQ's own `.gitignore` un-ignores `*.mjs`, and a test fails if git would ignore a file the application needs (G4) | The repository HQ sits in ignores `*.mjs`, so `next.config.mjs` and the mutation runner were never committed | — |
| 63 | The layout detector measures part-way down a page as well as at both ends, and looks through what the browser does not draw (G6) | A covering seen only part-way down a long page was missed, and invisible elements were reported | Rewording the limit in docs/KNOWN-GAPS.md only |
| 64 | A sign-in name over 41 characters or a passphrase over 1,024 is refused at once, before any other work; the throttle itself refuses names and device ids over 64 (G7) | A lane was keyed by the whole name the client typed, so long names could fill the server's memory | — |
| 65 | When the throttle is full it forgets first a lane with nothing in progress and fewer than five failures (or an expired count), then one with nothing in progress, never one with an attempt in progress (G8) | Forgetting the least recently used lane let a flush of fresh names reset the count of a name under attack | Forgetting the least recently used lane, whatever its state (the earlier rule) |
| 66 | Every MCP answer carries `x-request-id`, and the 401 and the cross-origin refusal are logged with it (G9) | Some answers carried none, though the documents said they did | Correcting the documents only |
| 67 | The conformer is domain logic (`src/lib/domain/conform.ts`). The store keeps each loaded revision in two forms, as stored and conformed; every reader and every derivation uses the conformed view, whose type the derivations require, and every write-path check uses the stored records. An answer that names a record that is not valid says so, with its problems and its stored form (G11a) | The screens were conformed, but the REST and MCP tools computed on the records as stored, and nine of them answered 500 while such a record was stored | Hardening each of the derivations' field reads; conforming in the transports only |
| 68 | One proposal-impact function (`services.proposalImpact`), given the page's loaded dataset: references from the conformed view, “before” values and the target's acceptance as stored (G11b) | The review screen used a copy the tests did not exercise | Keeping the copy and testing both |
| 69 | A passphrase longer than sign-in accepts cannot be set (G11c) | Sign-in refuses it before checking it, so it would lock its person out | — |

## Decisions made after the re-check of the third round

The third round was re-checked (docs/PROGRESS-REGISTER.md). Numbers 70 to 82 correspond to the
fourth-round decisions H1 to H13. The aim of the round was fewer rules that say more: where one
simple rule could close a class of defect, it replaced the special cases.

| # | Decision | Reason | Alternative set aside |
| --- | --- | --- | --- |
| 70 | What enters through the inbox is the submitter's claim: in the record a proposal would leave, a source label (`reported`, `design_intention`, `source_recommendation`, `founder_statement`) must be identical, as a whole object at the same place, to what the record already holds; otherwise HQ403, rule `source_label` (H1) | HQ can check that a quotation's words are in a source, not that they are about what they are attached to, so any verbatim sentence let a module that exists only as a design read “Tested — not accepted” | Requiring a citation for a source label (the earlier rule); judging whether a quotation supports a claim |
| 71 | Evidence a source reports or HQ's build checked, and a source HQ has read, are frozen for proposals as a whole (H2) | Locking five named fields left the title, module and links open, so reported evidence could be retitled and moved | Locking more fields one by one |
| 72 | A proposal cannot make a requirement implemented and tested, nor change the links of one that is (H3) | Linking any reported evidence, however unrelated, took a requirement off the outstanding list | Checking that linked evidence is about the requirement, which HQ cannot do |
| 73 | A proposal sets only the top-level fields its record type declares, from a table (`hq.record_fields`) kept equal to the schemas by a test; imports stay loose (H4) | Look-alike keys such as `"hq_acceptance "` and `Standing` passed every check that matched exact names | Making the record schemas strict, which would refuse a newer pack |
| 74 | A founder decision cannot clear an acceptance or rejection that is not there (H5) | Clearing nothing made HQ say that an earlier acceptance or rejection had been cleared | Changing only the wording of that caution |
| 75 | A record that fails validation never counts as proof, is flagged on every module whose id its stored data holds, takes only defaults that assert nothing, and its marker “Not a valid value” can never be written back by proposal (H6) | Conforming kept some values that still counted (evidence that fails validation was still an acceptance instrument) and dropped negative ones (blockers, a defect's module list) | Repairing each derivation's reads one by one |
| 76 | Errors echo at most 80 characters of what the client sent and list at most 10 items with a count; refusal rows of callers without an identity are written in full up to 120 a minute per action and reason, then counted in a summary row (H7) | A 1 MB request gave an error of 4.7 MB, and unauthenticated requests wrote audit rows without limit | Writing every refusal in full, and saying so |
| 77 | Every API route answers every standard method with a request id: a shared handler gives 405 with `Allow`, or 204 for `OPTIONS`; health stays the one exception (H8) | The 405 the framework made for a method a route did not export carried no id, contrary to the documents | Setting the header in middleware; narrowing the documents |
| 78 | Migration never changes the password of an application role that already exists, unless `HQ_ALLOW_ROLE_PASSWORD_CHANGE=1`; it stops before anything is applied (H9) | The role belongs to the whole server, so a second installation's setup broke the first one's connection and let its own password open the first one's database | Only documenting it |
| 79 | The layout detector leaves out a box clipped away entirely, by the same hit test check 4 uses, and also measures where each sticky element is stuck; what it still cannot see is listed in docs/KNOWN-GAPS.md (H10) | A fully clipped box was reported as a covering, and a sticky covering present over a short scroll range was missed | Looking inside iframes and shadow roots |
| 80 | `hq.log_access` accepts an exact list of actions, its tool names from a table (`hq.tool_names`) kept equal to the registry by a test; a session row names only the caller's own handle; `hq.log_refusal` stays open, because a refusal names what was attempted (H11) | A list of refused words could not cover every wording: `tool.sign_off` and `api.founder_signed_off` went through | A longer list of refused words |
| 81 | At acceptance the application runs its own copies of the rules first, in the database's order, so a refusal carries the same `detail.rule` and `detail.field` as at submission; the tests the verifiers showed missing are added; a record type in a refusal is cut to 40 characters (H12) | At acceptance the database answered first, without the detail the documents promised | Saying in the documents that a refusal at acceptance carries less detail |
| 82 | Every sentence the verifiers quoted as false in these documents is corrected against the code, and the generated reports are described as reports of the commit each names (H13) | Several sentences said more than the code did, and old reports read as if they described the current code | — |
| 83 | Fifth and last round (K1–K9), NOT re-checked by anyone: a record that carries a positive status from an import is frozen for proposals unless the proposal withdraws that status (a loop or pathway a source describes, a requirement shown as tested), what identifies a build and a module's evidence level are protected, and every list and count leaves out what HQ cannot read | The re-check of the fourth round showed imported labels left on content a proposal had rewritten, and lists that still counted records HQ cannot read | Marking each changed field beside the imported claim instead of freezing the record |
| 84 | Each API token has its own rate limit, a token bucket held in memory (default 120 a minute, burst 30; HTTP 429 with `Retry-After`); an MCP batch costs one per message and a batch larger than the burst is refused outright; refusals are audited at most once a minute per token; founder sessions are exempt (HOST-P1) | Needed before any AI client is connected to a hosted HQ: a misbehaving client could otherwise keep HQ busy | A limit per client address (an AI platform shares addresses across customers); a limit in the database (every request would write) |
| 85 | The hosting design runs HQ and PostgreSQL on one small Ubuntu 24.04 server, both on loopback only, with SSH as the only open port; the founder reaches the screens through an SSH port forward; AI clients reach only `/api/mcp`, through a separate loopback gateway, once the founder approves (docs/HOSTING.md) | The simplest arrangement that never exposes the database or the founder screens | A managed database (more cost, more moving parts); a public HTTPS site for the screens |
